则该决策已丢失且**不会在文档里留下痕迹**。

届时补记本表并修订设计方案。

## 6. ★ 一个反复出现的教训（v1.2 记）

**"测试通过但什么也没验证"** 已出现三次：

| # | 场景 | 表象 |
|---|---|---|
| 坑 41 | `assert "★" in output` | 脚注里的说明文字也含 ★ ⇒ 恒真 |
| 坑 44 | 路径泄露扫描 | config 注释里的反例被命中 |
| 坑 37 | 作者归一化 | 只处理了 `J. Doe`，漏了 `DOE, John` ⇒ 同作者两个 hash |

共同点：**测试打在了"看起来对"的东西上，而不是真实结构。**
→ 已固化为红线 18；写断言前先问"这条断言在什么情况下会**恒真**或**恒假**"。

## 7. ★ L1-A 留下的最重要一个实测（v1.4 记）

```
31,542 条 references  →  命中库内 3 条  →  0.0095%
```

**这不是 bug**（随机期望约 6.9 条，实测 3 条同数量级），是真实的冷启动稀疏，

## 8. ⚠️ 一次流程事故（v1.4 记，用于警示）

**2026-10-24，L1-A 验收后**：我在回复中声称三份文档已刷新到 v1.6/v1.4/v1.3 并交付了文件，
但**实际没有执行刷新**——交付的仍是旧版本（v1.5/v1.3/v1.2）。

**发现方式**：下一轮执行 v1.7 修订时，脚本的锚点断言失败，grep 才发现版本号没变。

**根因**：我把"文档刷新"当成可以顺手完成的事，没有落到执行步骤。
这与 §5 第 5 条（里程碑收尾必须刷新）是同一个问题——**纪律写了不等于执行了**。

**对策**：刷新文档必须**实际执行文件写入**，交付前用 `grep` 核对版本号。
