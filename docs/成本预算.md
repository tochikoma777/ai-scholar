## 3. 闸门设计（硬约束）

1. **预算决定「做多少篇」，不决定「单篇做多浅」** —— 质量由 prompt 与上下文保证，
   **绝不因预算截断单次生成**；钱不够 = 少做或进队列，不是降质。
2. **闸门在「调用前」**：每次 LLM 调用先按 `输入估算 token × 单价 + max_tokens × 输出单价`
   预估，累计到当日额度即**不再发起新调用**，任务进队列不丢弃。
3. 四层上限 + 单次 run 调用次数上限，全部可配置（见 §4）；超限**硬停、退出码 0**。
4. 每次调用记账（tokens / 模型 / 估算成本 / 缓存命中与否）→ `llm_usage` 表，
   每日报告尾部附**成本说明**（当日实际 vs 当日额度 vs 累计）。

## 5. 叠乘反例（为什么闸门卡「篇数 × 上下文」）

```
500 篇/天 × 50k 全文 × 1 元/M = 25 元/天 ≈ 9,000 元/年
```

单看单价不贵，一次「图省事对全量做深度分析」就是 **60 倍**。因此闸门必须同时卡：
每日篇数、单次上下文上限、单次 run 调用次数，缺一不可。

```bash
uv run ai-scholar cost              # 今日 / 滚动 7 日 / 本月 / 本年 / 全部 + 分项 + 异常标注
uv run ai-scholar cost --days 30    # 换窗口（中位数与环比同步换）
uv run ai-scholar cost --json       # 字段稳定，供脚本/告警消费
```

**口径（写死在 `pipeline/cost.py`，别混）**：

| 数据 | 来源 | 可信度 |
|---|---|---|
| 今日 / 窗口 / 月 / 年 / 全部累计 | `data/reports/*.json` 的 `cost_cny` | ★ **真源**（public、跟 git 走、可审计） |
| 按 purpose 分项 | db `llm_usage` | ⚠️ **缓存**（Actions 重启可能丢），只用来判断"哪一步贵" |

**异常判定（只标注，不阻断；退出码恒 0）**：
1. 今日 > 日限额 × 0.5；
2. 今日 > 近 N 日（不含今日）中位数 × 3（中位数为 0 时跳过——不拿 0 冒充）；
3. 本月 > 月限额 × 0.8。

★ 坏报告文件（JSON 解析失败 / `cost_cny` 为 null / date 非法）会作为"提示"打印，
**不静默跳过** —— 少算一天的成本账比多报一天更危险。

### 10.1 异常会出现在哪三处（都只标注、不阻断）

| 位置 | 表现 | 谁能看到 |
|---|---|---|
| 每日报告 md | 顶部 `> ⚠️ **成本异常**` + 逐条原因 | 打开报告的人 |
| 每日报告 json | `cost_anomalies: [...]`（结构化，字段稳定） | 脚本 / 站点 |
| 静态站点 | 「成本」板块顶部红色 badge + 近 N 日柱状 + **7 日均线（折线）** + 异常日红点 + 本月累计 | 看板 |
| Actions run | `::warning title=成本异常::...`（run 页面标黄 + 通知邮件） | 你 |

★ **不进 `degraded`**：`degraded` 表示"数据源故障"，成本异常是"花钱异常"，
两者混在一起会让"报告里降级很多"变成噪音。

## 11. 2026-11 成本异常复盘 + 削峰（L9-E）代价评估（2026-11-10）

### 11.4 ★ 撤回"缓存假设"：差额不是 batching 造成的

上一轮口头解释是「5 篇挤同一 run 共享长 prompt 前缀命中 DeepSeek 上下文缓存
（cached ¥0.025/M vs miss ¥3/M），摊成 1 篇/天后每次 cache miss」。**该解释不成立**：

1. `deep_analysis` 把整个 prompt 作为**单条 user message** 发送
   （`pipeline/deep_analysis.py` 的 `llm.complete([{"role":"user","content":prompt}])`），
   模板 `prompts/deep_analysis.j2` 固定部分只有 5.5 KB（约 2~3k token），
   从第一个变量（`paper_id` / `title`，模板第 45 行起）开始每篇就不同，正文
   （`{{ fulltext }}`，第 55 行）更是完全不同。
2. DeepSeek 上下文缓存只对**相同前缀**生效 ⇒ 可共享的只有开头那 2~3k token。
   按 v4-pro 单价差 ¥3.0/M → ¥0.025/M，单次最多省
   `2.5k × 2.975 / 1M ≈ ¥0.0074`；5 篇里后 4 篇共享 ⇒ 整批最多省 ¥0.03，
   摊到每篇 **≈¥0.006**，只占实测差额（¥0.058~0.076）的 10% 左右。
3. 能解释这个量级的是**每篇正文长度**：`config/default.yaml` 注释记录 arXiv 正文实测
   **38k~184k 字符**，`max_fulltext_chars=100000` 只是上限、超限才中间省略。
   38k 字符 ≈ 11k token（¥0.034，miss 价），100k 字符 ≈ 30k token（¥0.090，miss 价），
   单是输入就差 **≈¥0.056**；再叠加 strong 档推理输出长度差异，正好覆盖 ¥0.058~0.076 的缺口。
   11-02 那批「全文命中 4/5」（1 篇只有摘要、近乎免费），11-09/11-10 两批「全文命中 1/1」。

⇒ **差额主要由"分析了哪些论文"（正文长度 / 推理长度）驱动，不是"几篇一起跑"。**
另外新节奏下候选池仍是 D 排序 Top 5（`default_limit=5`，11-09/11-10 日志均为
「本次选中 5 / 预算配额拦截 4」），只是每 run 只落地 1 篇；由于 D 排序的热度项按
`trending_lookback_days=1` 每天重算、且已分析论文被去重，一周下来的 5 篇
**不是同一组论文**，两组样本不可直接相减。

**待坐实**：`llm_usage` 表逐调用记有 `tokens_in` / `tokens_out` / `cache_hit`
（见 `budget.py`），但该表在 Actions 缓存 db 里、**不入库**，public 产物只有汇总 `cost_cny`。
要最终确认需查 Actions 缓存 db，或配 key 本地实跑一次并读 `llm_usage`。

### 11.5 成本差距量化（两种口径都要看）

| 口径 | 数值 |
|---|---|
| 已观测：W45 旧节奏（5 篇挤 11-02 一天） | `weekly-2026-W45` 区间合计 **¥0.4972**（7/7 天） |
| 已观测：W46 新节奏前 2 天 | ¥0.1464 + ¥0.1778 = **¥0.3242** |
| 外推：W46 满周（5 个分析日 ~¥0.15 + 2 个基线日 ~¥0.03） | **≈¥0.83/周** |
| 表面差额 | **≈+¥0.33/周 ≈ +¥17/年**（若单价维持） |
| 其中可归因于 batching 共享前缀缓存的部分 | **≈¥0.03/周 ≈ ¥1.8/年**（理论上限，< 10%） |

★ 「+¥17/年」是**混淆对比**（旧样本仅 1 组、论文不同、且含 1 篇无正文），
**不能当作"削峰导致的成本"**，更不能当作"改回 batching 能省下的钱"。
两种节奏每周都消耗 5 篇 `analyze` 配额，差别只在论文集合与分布。

### 11.6 结论与建议（供负责人评估"是否改回每周挤同一 run"）

1. **不建议为省钱改回 batching**：理论可回收的只有共享前缀缓存 ≈¥1.8/年；
   却会重新引入 ¥0.31 单日尖峰、相对突增告警、以及 6 分钟单 run 的强档调用。
   `budget.daily_limit_cny=2.0` 从未被突破，尖峰本身不是预算问题。
2. **真要降本，动 `deep_analysis.max_fulltext_chars`**（100000 → 例如 40000）
   比改节奏有效得多：直接砍输入 token，与配额语义正交，且不改变 1 篇/天。
   ★ 属 L3 成本口径变更，需负责人批准；改前用 `budget --input-tokens N --max-tokens M` 演练。
   ★ **2026-11-11 补充**：负责人优先选择了「换模型」这条降本路径（默认 strong 档改 flash，
   见 §12），而非砍正文长度 —— 保留全文是为了不牺牲六段/透镜的证据密度；`max_fulltext_chars`
   维持 100000 不动。本节建议 2 保留为「若还要继续降本」的备选，未执行。
3. **严谨验证**：等 2026-11-15 满一周拿到 5 个 1 篇/天样本再比；若要受控 A/B，
   临时把 `daily_limit` 调回 5 跑一个周一一 run（成本 ≈¥0.3~0.6），
   **按治理协议需先批准这笔花费**。
4. **L10 A-4「无未解释异常」**：11-02 / 11-09 / 11-10 三天已在本节逐条给出根因，
   视为**已解释异常**；另有 L9-E 两条预测未兑现，已在本节标注，不构成未解释成本。
5. **不要改 `detect_anomalies` 的 ×3 中位数规则**：11-09/11-10 是分布切换期的短暂假阳性，
   约 11-13 起自愈；为它调规则会削弱真实异常的检出能力。

  UTC 20:00–00:22 = 北京 04:00–08:22，**都在空闲窗口**。
- 但最近两次是 UTC 21:53 与 **00:22（北京 08:22）**，距 9:00 高峰仅 **38 分钟**
  ⇒ 延迟再长一点就会踩线。

### 13.3 守卫策略（`utils/peak_hours.py` + daily 的 `Peak-hour guard`）

- 判断：UTC 工作日（周一–周五）+ 窗口 `[01:00, 04:00)` / `[06:00, 10:00)`，
  **前后各留 15 分钟余量**（guard 到真正发 LLM 调用之间还有若干分钟）。
- 命中高峰 ⇒ 往 `$GITHUB_ENV` 写 `AI_SCHOLAR_MODE=off` + `::warning::`：
  `enhance` / `grade` / `analyze` 三处 `RunMode.OFF` 早退 ⇒ **零调用**；
  `report` / `site` / `predict` / `cost` 等零 LLM 步骤照跑；次日空闲自动补跑（周配额 5 篇不丢）。
- **不 sleep 到空闲**：job `timeout-minutes: 60` 不够（延迟已 4–8h），且跨过 UTC 16:30 会改
  `today_local()` 北京归属日、让日报日期错位。
- **不改 cron**：避免破坏日报归属日与 `recap.yml` 的
  `if: github.event.schedule == '35 16 * * 1' / '35 16 1 * *'` 字面量；
  也避免动 `concurrency` 排队语义（`test_workflows.py` 有机械校验）。
- **保守忽略中国法定节假日**：把节假日也当高峰 ⇒ 只会多降级、不会漏进高峰。
- 机械门禁：`tests/test_peak_hours.py`（边界）+ `tests/test_workflows.py`
  （守卫存在、位于 LLM 步骤之前、常量与官方一致）。

### 13.4 ⚠️ 待定案：项目价格表与官方分时价不一致

`config/default.yaml:51-62` 与本文 §1 的价格表是**单一平价、核对日期 2026-10-24**：

| 模型 | 项目表（命中/未命中/输出） | 官方空闲 | 官方高峰 |
|---|---|---|---|
| `deepseek-v4-flash` | 0.02 / 1 / **2** | 0.02 / 1 / **4** | 0.04 / 2 / 8 |
| `deepseek-v4-pro` | **0.025 / 3 / 6** | **0.15 / 4.5 / 13.5** | 0.30 / 9 / 27 |

⇒ 项目表**偏低**（尤其 pro 与输出价），预算闸门/记账会**低估**真实花费；而守卫保证的是
「按空闲价计费」，两者是不同问题。**本轮不改价格表**（属成本口径 L3，需负责人定案）：
若要改，需同步 `config/default.yaml` 的 `budget.prices` + 本文 §1 + 闸门回归测试，
并决定是否按「空闲/高峰」两档计价（或在代码里按时段选价）。
