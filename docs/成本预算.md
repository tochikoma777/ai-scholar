### 2.1 实测回填（L3a，2026-10-24）

- 环境：`deepseek-v4-flash`，1 篇条目增强 + 10 条关联解读 = **11 次调用，实测 ¥0.002659**。
  - 条目增强：1 次，¥0.000792（输入 795 / 输出 388 tokens）
  - 关联解读：10 次，¥0.001867（输入 8559 / 输出 848 tokens）
- `json_schema` 被服务端拒绝（400）→ 自动降级 `json_object`，成本按**实际 token** 记账。
- ★ 上表「0.011 元/次」是**按 max_tokens=4000 的保守估算**；实际按 token 计费明显更低，
  预算闸门仍用保守估算，避免低估。

## 3. 闸门设计（硬约束）

1. **预算决定「做多少篇」，不决定「单篇做多浅」** —— 质量由 prompt 与上下文保证，
   **绝不因预算截断单次生成**；钱不够 = 少做或进队列，不是降质。
2. **闸门在「调用前」**：每次 LLM 调用先按 `输入估算 token × 单价 + max_tokens × 输出单价`
   预估，累计到当日额度即**不再发起新调用**，任务进队列不丢弃。
3. 四层上限 + 单次 run 调用次数上限，全部可配置（见 §4）；超限**硬停、退出码 0**。
4. 每次调用记账（tokens / 模型 / 估算成本 / 缓存命中与否）→ `llm_usage` 表，
   每日报告尾部附**成本说明**（当日实际 vs 当日额度 vs 累计）。

## 5. 叠乘反例（为什么闸门卡「篇数 × 上下文」）

```
500 篇/天 × 50k 全文 × 1 元/M = 25 元/天 ≈ 9,000 元/年
```

单看单价不贵，一次「图省事对全量做深度分析」就是 **60 倍**。因此闸门必须同时卡：
每日篇数、单次上下文上限、单次 run 调用次数，缺一不可。

## 6. 报告成本说明格式（约定）

```
## 成本
- 当日：实际 ¥X.XXXX / 额度 ¥2.00（用量 N 次，输入 A tokens，输出 B tokens）
- 本月累计：¥Y.YYYY / ¥40.00
- 单价：flash in-miss ¥1/M · out ¥2/M（核对日期 2026-10-24）
```

> ★ 附此说明的目的：当 API 供应商调整收费，前期估算会失效 —— 实测数字让账单偏差
> **当场可见**，而不是年底才发现。
