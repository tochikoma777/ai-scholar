## 治理类（2026-10-24 与负责人商定）

### G1 全权 ≠ 无人驾驶
执行与文档全权交给 Agent，但 **push / tag / 不可逆操作必须逐次授权**。
**判据**：一个动作能否靠 `git` / 重跑找回 —— 找不回就报批。
**反例**：推 tag 上 public 不可逆；`export --all` 批量建笔记会让 vault 不可逆膨胀。

### G2 花钱路径先列后做
任何新增 LLM 调用点 / Actions / 第三方 API，开工前给出「单次 / 日 / 月 / 年」估算，
上线后**实测回填**。`off` 档必须恒 0。
**判据**：报告里出现"预计花费"却没有"实际花费"，视为未完成。

### G3 预算卡「调用前」，不卡「生成中」
**原则**：钱不够 = 少做或进队列，**不是降低单篇质量**。闸门在发起调用前预估并拦截，
绝不中途截断生成。
**反例**：为了不超 max_tokens 而让模型回显摘要、砍掉六段之一 —— 那是质量事故，不是省钱。

### G4 交接文档要能「盲测」
阶段交接文档质量门槛：**新 Agent 只读 CODEBUDDY.md + handoff 能独立跑通并说出风险**。
写法：写完后自己不看对话、照文档走一遍，走不通就是不合格。

### G5 本地开发不得覆盖公共真源（2026-10-25 实锤）

**规则**：`data/reports` / `data/signals` / `data/predictions` / `data/first_seen.jsonl`
由 **daily bot** 负责提交；本地跑管道后**不要把它们一并 commit**。

**Why**：L4 提交时顺手 `git add data/`，把本地 `2026-10-25` 报告覆盖到 bot 产物上：
bot 版含 `runs=1` + `degraded={hf_daily: HTTP 400}`，本地版变成 `runs=0` + `degraded={}`。
结果**降级证据在 public 产物里消失**，而日志里明明有 HF 400。这不是代码 bug，
是数据来源被本地缓存覆盖 —— 比代码 bug 更难发现。

**How to apply**：
- 提交前 `git status` 看清 `data/` 改动来源：本地 `report` 生成的报告不要提交；
- 只有需要修正历史产物时才手动改 `data/`，并在 commit message 说明来源；
- `site` / `report` 展示降级信息依赖 `runs.degraded_json`，真源被覆盖 = 面板"看起来正常"。

## 成本类

### C1 成本失控是「叠乘」，不是「单价」
```
500 篇/天 × 50k 全文 × 1 元/M = 25 元/天 ≈ 9,000 元/年
```
单看单价不贵，一次「图省事对全量做深度分析」就是 60 倍。
**原则**：闸门必须同时卡「篇数 × 上下文长度 × 调用次数」，缺一不可。

### C2 单价模型要三档，单一数字必错
计费是「输入命中 / 输入未命中 / 输出」三档，输出单价常是输入的 2 倍。
**反例**：`config/default.yaml` 原 `price_fast_cny_per_1m: 1.0` 单一数字，无论怎么填都系统性低估。

## 工程类

### E1 死配置要么接消费者，要么写明「消费方在哪个阶段」
**判据**：每个配置项在源码里 grep 得到消费方，否则视为未完成。
**历史反例（已修复，勿再当作现状）**：`similarity_strong_weight`（0.30）曾无人读 ——
留下"看起来已实现"的假象；L3a 接线后由 `pipeline/enhance.py` 消费（选强相似边做关联解读），
`budget` 块亦已被五个模块消费。**原则不变**：看到"随对应阶段接入"这类措辞就建任务卡。

### E2 测试绿 ≠ 功能完整
206 测试全绿、`export --check` 0 变更，仍漏了三个洞（无笔记边不显示相似度 /
`--dry-run` 把存量报成新增 / 死配置）。
**原则**：推送前按任务卡 DoD 与「可解释性 / 幂等 / 降级」三条逐一对，不看 pytest 数。

### E3 断言打在「真实结构」，不打在「看起来对」的东西上
**反例**：`assert "★" in output` 命中脚注说明文字 → 恒真（本项目已三次踩中，红线 18）。
**判据**：写断言前先问「这条断言在什么情况下恒真 / 恒假」。

---

### E4 统计分母必须显式排除「无法判断」

命中率的分母只能是 **hit + miss**；`insufficient`（数据不足）与「观点」都要单独列。
**反例**：把"样本不足"算成 miss，会让早期命中率虚低；算成 hit 则会美化评测。
**判据**：任何比率输出都要能回答「分母是什么、排除了什么」。
**落地**：`pipeline/stats.py` 的 `insufficient` 不进分母；`opinions.jsonl` 永不进统计。

### E5 失败信息必须能自证，不能只报状态码

**规则**：对外部源的失败，错误文案要带**截断的响应体**与请求关键参数
（URL / 日期）。`HF HTTP 400` 这种只有状态码的消息，等于让下一个人从零猜。

**Why**（2026-10-25 实锤）：排查 HF 400 时 daily 日志只有 `HF HTTP 400`，
第一反应是「网络 / 镜像 / IP 被限」。实测镜像与官方同行为，才发现
官方 API 对「今天」直接 400：`"date" must be less than or equal to "<今天>"` ——
是**榜单发布延迟**，正确修法是把窗口改成从昨天开始，而不是换源。

**How to apply**：
- 采集器抛错时附 `response.text[:300]`（去换行），并带日期 / URL；
- 判据：只看错误信息，能否直接分清「是源的问题还是我们的参数问题」；
- 连带教训：外部源的能力与边界**先实测再接线**（D1），尤其"边界值 / 回退源"。

### E6 max_tokens 要按「推理 + 答案」设，不能按答案长度设

**规则**：给带推理的模型设 `max_tokens` 时，预算 = **推理 token + 正式答案 token**，
只按答案长度估必翻车。

**Why**（2026-10-25 端到端实测）：`max_tokens_fast=4000` 下，定级输出停在定级表表头，
`tokens_out=3999` 正好顶格 —— token 被推理吃光，答案被截断，`Tier` 解析失败。
抬到 8000 后同一次请求即成功。`max_tokens_strong=8000` 也已顶格（两次深度分析
`tokens_out≈7998`），属于侥幸没截断。

**How to apply**：
- 改 `max_tokens` 前先看 `llm_usage.tokens_out` 的**实际分布**，不要拍脑袋；
- 出现「结构化输出缺尾 / 解析失败」先查 `tokens_out` 是否顶格，再查 prompt；
- 抬上限不强制多产出（输出按实际计费），但**要复跑确认成本没异常**；
- 截断的自愈机制已设计好：解析失败 ⇒ 不写指纹 ⇒ 下次重试，不要为了"这次成功"降低质量要求。

### E7 验收必须查「跨阶段接缝」，不能只验收「能力」

**规则**：阶段 DoD 除了验收本阶段能力，必须显式回答一句——
**「本阶段的产出，下一个阶段/最终用户凭什么拿到它？」**答不上来就是接线缺失。

**Why**（2026-10-25 L7 前置审计实锤）：
- `deep_analysis.py` 的双通道选篇代码**早就写好了**，报告的「深度分析」板块
  （`daily.md.j2` + `report.py`）**也早就写好了**，但：
  - `analyze` **从未接入任何自动管道**（唯一调用者是 CLI）
  - 深度分析完成 **不置 `selected`**（全仓库只有 `mark` 写它）
  ⇒「每日一篇 → 深度分析 → 沉淀进 vault」整条链**两头断在接线处**，
  而每个阶段都是绿灯——因为 L3b-2 的 DoD 是「对 1 篇真实论文跑出完整分析」，
  按这个标准，能跑就算过，接不接管道不在验收范围。

**根因**：设计文档 §5.6 写明「置位途径**随对应阶段接入**」，但**没有任何阶段的
任务卡把这三条途径列为 DoD** ⇒ 无主事项，一路合法放行。

**How to apply**：
- 写阶段 DoD 时，对每个"以后要用"的字段/产物，指定**唯一责任阶段**并写进该阶段 DoD；
- 收尾自查（E2）增加一项：`grep` 该产物的**写入点**，确认不是"只有我一个人在写"；
- 看到"随对应阶段接入"这类措辞，立刻建任务卡，不允许停留在散文里。

## 数据类

### D1 能用实测替代推断的，不要推
引用命中率推了三轮都错，实测一次即推翻（0.0095% ≈ 零）。
**原则**：体积 / 关联 / 命中率这类量级判断，先实测，不靠推断。拿不到真值就 `skip`，不伪造。

★ **反例（2026-10-25）**：曾据「ar5iv 是 arXiv HTML 镜像」推断它可作正文回退源；
实测发现它对**有 HTML 和没有 HTML 的论文都只返回约 5k 字符的 arXiv 摘要页**（导航 + 主题分类），
不是正文。若照推断实现，prompt 会误以为有全文，比返回 `None` 更糟。
⇒ **外部源的能力先实测再接线**，尤其是「回退源」——错的回退会伪装成真数据。

### O2 阶段收尾 = 下一阶段 handoff 就位（clear/init 前置）

**规则**：每个大阶段宣布完成前，必须**新建** `docs/handoff/L{下一阶段}-开工.md`；
当前阶段文件标「已归档」并指向新文件。下一阶段 Agent 只靠它恢复上下文。

**Why**：每个大阶段结束都会 **clear + init**，上下文归零；handoff 缺失 = 下阶段在无上下文下开工。
2026-10-25 实际发生过：把 L4 内容写进 `L3-开工.md`，文件名仍锚定 L3，靠负责人提醒才发现。

**How to apply**：
- 收尾清单显式包含「新建下一阶段 handoff」+「当前阶段归档」；
- 跑 `uv run pytest tests/test_docs_consistency.py -q`（机械校验下一阶段 handoff 存在且未归档）；
- ★ **不要只改现有 handoff 的内容** —— 文件按阶段命名，**内容更新 ≠ 交接完成**。

### E8 「判废」要看顶格，不能只看"有没有内容"（2026-10-26 Actions 实锤）

**规则**：结构化 LLM 输出的验收 = 骨架 + 长度 + **`tokens_out` 是否顶格**。
顶格 = 推理把额度吃光，答案即使"看起来有结构"也是残稿；空内容 + 顶格 = 纯烧钱。

**Why**：strong 档带 100k 正文时，`max_tokens=8000` 被推理吃满（`tokens_out=8000`、
`content` 0 字符），5 次调用只 1 次成功，**80% 花费是废调用**（¥0.2361）。
更隐蔽的是：当时的判据是"`paper_id` 是否回显"——真实模型经常不回显，
于是把"截断"误诊成"不听话"，修错方向。

**How to apply**：
- `validate_output(content, tokens_out=..., max_tokens=...)`：空/短/缺骨架/顶格，四种都判废；
- 判废理由必须带 **tokens_out 与字符数**（否则下一个人只能猜，E5）；
- 抬 `max_tokens` 前先看 `llm_usage.tokens_out` 的分布，别按"答案长度"估（E6）。

### E9 预算保护要「口径对齐产出 + 连续失败刹车」（2026-10-26 负责人定性为严重缺陷）

**规则**：① 任何"配额/预算"的口径必须与**产出**对齐（篇、条），不能按"尝试次数"；
② 同一批里连续失败 N 次（默认 2）必须**中止本轮**，不许把剩余候选一路付费烧完。

**Why**：首次 Actions 里 4 次废调用按"调用"计直接吃掉整周 5 篇配额 ⇒
之后一周无法分析（`blocked=5`），钱花了、额度也没了 —— 双重浪费。

**How to apply**：
- 写配额逻辑前先问："这个数代表**产出**还是**尝试**？"；
- 失败是信息：连续失败通常意味着系统性原因（额度不足 / 模型不兼容 / prompt 崩了），
  继续重试只会放大损失；
- 刹车后必须把"已花成本 + 中止原因"写进 `degraded`，让人知道为什么停。

### E10 判废 / 记账规则要落**在每个** LLM 调用点上，不能只落在一处（2026-10-26 审计）

**规则**：新增或改动 LLM 调用点时，同时检查三件事：
① 输出判废是否用**结构 + `tokens_out` 顶格**（不是"模型有没有回显 id"，E8）；
② `llm_usage` 记账是否在**解析/校验之前**（钱已经花出去了，漏记 ⇒ `cost` 与预算闸门失明）；
③ 连续失败 N 次是否刹车（E9）。

**Why**：E8 / E9 只在 `deep_analysis` 上落地；`grade` 仍用「`paper_id` 是否回显」判废 ——
真实模型经常不回显 ⇒ **每天重复付费重定级**，且失败不刹车；`enhance` 把记账写在
解析成功之后 ⇒ 解析失败的那 1/29 笔花费在 `cost` 里**完全不可见**。

**How to apply**：判废实现共用 `llm_support.validate_output`（同一份代码，不重复实现）；
记账一律紧跟 `llm.complete` 之后；新增调用点照抄 `deep_analysis` 的那段顺序。

### E11 「只取最新一条 run」的查询会吞掉降级证据（2026-10-26 审计）

**规则**：从 `runs` / 状态表读"最近状态"时，先问**"最近一条是不是代表全部？"** ——
一个 run 只记**一个源**，取最新一条等于只看到最后那个源。

**Why**：daily 的最后一步采集是 `collect --classics`，它写最新一条 run 且通常干净；
`_hf_degraded` 只读这一条 ⇒ 当天 HF 的降级证据被整个吞掉，vault / 报告看起来"一切正常"
（比报错更危险，同 G5）。

**How to apply**：按 `source` 取"最近一次该源的 run"；没有 source 的历史数据再退回按
`degraded` 键扫描。同类隐患：任何 `order_by(desc(...)).first()` 都要过这一问。

## 文档体系类（W，2026-10-30 文档体系自查新增）

> 分工：G = 治理 / C = 成本 / E = 工程 / D = 数据 / O = 输出规范 / **W = 文档体系**。

### W1 文档纪律必须**可执行**，否则等于没写

**规则**：每条文档纪律问一句「它能不能被一条命令判定红绿」。能 → 写成测试；不能 → 别写进文档。

**Why**：本项目三处纪律原本只是散文（"阶段收尾要有下一阶段 handoff""CODEBUDDY 里的行号要对"
"历史 handoff 要标已归档"），结果 2026-10-25/26 连着踩 —— 每次都是**人工核对不可靠**。
改成 `tests/test_docs_consistency.py` 后，指针指错、行号漂移、归档漏标都会让 CI 红。

**How to apply**：
- 文档里出现的**路径引用**（索引表/卡引用）→ 断言文件存在（防幽灵引用）；
- 文档里出现的**行号锚点** → 断言该行确有该符号；
- 文档里的**状态字段**（阶段/基线/测试数）→ 断言与代码或另一份文档一致；
- **反向验证**：门禁测试里必须有"故意破坏 ⇒ 必须报错"的用例，否则门禁本身可能是假的。

### W2 文档按"意图 / 执行 / 记录"分层，禁止一份文档管所有事

**规则**：至少分四层，各层只答自己的问题，不互相抄：
① **意图 SSOT**（为什么这么做，改=改共识）② **执行规矩 / 手册**（怎么做）
③ **账本**（时间账 + 版本账）④ **交接 / 任务卡**（当阶段交付口径）。

**Why**：all-in-one 文档必然腐坏 —— 内容一多就没人读，没人读就没人更新。
本项目 1100 行的设计方案只能靠"读负责人点名的章节"，正是因为它是**意图**文档、
不是操作手册；反过来操作手册也不承载"为什么"。

**How to apply**：新增内容前先问"它属于哪一层"，落错层就是噪声。
每层内部再问：**删掉它，别的文档能不能回答它负责的问题？** 能 → 冗余，别加。

### W3 "文档 ↔ 代码"要有一本账，且更新顺序固定

**规则**：维护一份**文档版本账**（文档 ↔ tag ↔ 日期 ↔ 状态），
更新顺序固定为「先提交代码 + 打 tag → 再刷新账本」。

**Why**：账本要记 tag 列；代码还没提交就写不出 tag 列 —— **写不出来就说明顺序错了**，
这条纪律的价值在于它可执行。反过来，账本滞后就失去"文档有没有跟着代码走"的判断力
（本次自查发现：设计方案已 v1.12，账本上还写 v1.11）。

**How to apply**：凡是登记在册的文档都要有行；新增/删除文档时同步增删行，
别只对"内容文档"记、不对 README/CHANGELOG/CONTRIBUTING 这类门面文档记。

### W4 文档的"过期规矩"比没规矩更危险

**规则**：治理/归属/流程类文字，改一次就**全局 grep 一遍同名规矩**（规矩常常在 2~3 个文件里各有一份）。

**Why**：本次自查实锤：`执行手册` §1.3 仍写"项目负责人刷新 SSOT、你不要改"，
而 CODEBUDDY 早已改为"2026-10-24 起全由 Agent 分级维护" —— 矛盾的两份规矩同时在仓库里，
新 Agent 会按**过期那份**行事（本次直接导致文档维护责任被推回给负责人）。

**How to apply**：改归属/流程/红线时，先 `grep` 关键词在项目里扫一遍，
把旧表述统一改成"X 年 X 月定案取代"或直接删除，**不留两份并存**。

### W5 引用不存在的文件 = 幽灵引用，必须清

**规则**：文档里提到的每条路径都必须是真实存在的；跨文档引用要能被机械校验。

**Why**：本次发现 `执行手册` §1.2 引用 `经验固化-通用开发原则.md`（"若项目引入"），
文件根本不存在。读者会去打开它、找不到、然后怀疑自己看漏 —— 这是最低成本、最高频的文档缺陷。

**How to apply**：在门禁测试里加"索引表逐项存在"的断言（W1 的落地）；
写文档时先确认路径，再写引用。

### W6 分析类文档不入库，结论类文档才入库

**规则**：**决策依据 / 体检报告 / 复盘**这类"过程分析"可以留在本地（gitignore），
它们一旦入库就要求"每次结论变了都要更新"，维护成本远高于价值；
**结论**才写进 SSOT / 经验固化 / 账本。

**Why**：负责人 2026-10-28 决定 `审查报告/` `功能总览` `项目复盘归档` 不入库。
此后 `git status` 不再被它们弄脏，`git add -A` 也不会误提交 —— 代价是换机后看不到，
但分析类文档本来就是"当时那次决策的记录"，不是长期真理。

**How to apply**：判断标准 = **半年后还要不要照它执行**。要 → 进 SSOT；不要 → 本地。

### W7 交接文档要有"启用清单"，不能只有"状态描述"

**规则**：阶段交接文档除了写"当前是什么状态"，还要写**翻到下一阶段时的机械步骤**（含顺序）。

**Why**：本项目 L10 草稿原本只有清单内容，启用时要靠记忆执行
（`git mv` 改名 → 改指针 → 归档上一阶段 → 登记 → 跑门禁）；
**顺序反了门禁必红**（先改指针会让"最大阶段号"判定失败）。
补成 §6 机械清单后，翻牌变成照着做。

**How to apply**：任何"以后才会启用"的文档，都写一段
「启用前置 → 步骤 1..N → 门禁命令」，并注明哪一步顺序敏感。

### W8 文档体系怎么建：从「意图 / 证据 / 门面」三层反推（含工作流文档单列）

**规则**：给新项目建文档时，按**三层 + 一类**配齐，每层只放"只有它能回答"的内容：

**① 意图层 SSOT（决策者执笔或批准）**
- 设计方案：回答「为什么这么做」—— 判据、边界、取舍；与代码冲突时以**它 + 决策者裁决**为准
  （不是默认代码错，也不是默认文档对）。
- 执行手册：回答「怎么做」—— 红线、坑位、环境分级、里程碑、收尾纪律。
- 版本账：回答「文档有没有跟着代码走」—— 文档 ↔ tag ↔ 日期 ↔ 状态。
- 花钱账本（若涉及外部 API）：回答「钱花在哪、上限多少」—— 价格来源 + 估算 → **实测回填**。

**② 证据与账本层（执行方写）**
- 数据源手册：**真实**响应片段（截断）、规模口径链；不可达写"未获得 + 原因"，禁止编造。
- 时间账（开发日志）：按时间的事实、实测、踩坑 —— 事故回溯第一站。
- 教训库（经验固化）：可迁移教训，编号沉淀，所有结论的最终回流地。

**③ 门面层（对外）**
- README（能力 + 命令 + 路线 + 合规署名）、CHANGELOG（按版本/里程碑记交付）、
  CONTRIBUTING（怎么参与）、Agent 工作手册（若用 AI 协作：架构、红线、改哪里先跑什么）。

**④ 工作流文档（**不属文档体系本体**）**
- 阶段交接（handoff）、任务卡（DoD + 范围）：**有时效、可归档、结论外流、不面向长期读者**。
  四条全中即工作流，别把它们算进"项目文档"。

**Why**：本项目的体例就是这么长出来的 —— 早期决策者执笔 ①②③ 的意图与规矩，
执行方只能写证据（数据源手册 / 开发日志）；后来全权开发才把笔全部交给执行方，
决策者转为"批准权 + 阶段牌"。**归属变了，但"意图归决策、证据归执行"的分层没变** ——
分层站得住，换谁执笔都不会乱。

**How to apply**：
- **准生证三问**：新建一份文档前先答「它回答什么问题 / 谁能改 / 什么时候作废」。
  第三问答不出的多半是过程文档 ⇒ 别入库，结论回流到教训库即可。
- **分层判据**：删掉它，别的文档能不能回答它负责的那个问题？能 ⇒ 冗余，别加。
- **规模纪律**：SSOT 变长（本项目 1501 行）是**正常的**，但要配"读指定章节"的导航约定；
  反过来，工作流文档必须短（本项目都 < 160 行）—— 长了说明它在偷当 SSOT 用。
- **能生成就别手写**：数据源手册由脚本实跑生成 ⇒ 永远不漂移；能这样干的文档都这么干。
- **双账本**：时间账（记事实，可废）+ 版本账（记版本，可审计），缺一个就回答不了
  "这个文档是不是过期的"。
- **反面清单**：别把工单/交接当文档体系（越攒越多）；别让对外门面承载内部约定；
  别在入库文档里引用不入库的文件（= 幽灵引用）。
