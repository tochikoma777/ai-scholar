# 经验固化

> 维护方：**Agent**。高质量的经验教训、实践出的原则与技巧、总结出的指南，都落到这里。
> **分工**（避免双写漂移）：坑位清单（`执行手册.md` §4）= 具体某个坑；`开发日志.md` = 按时间的事实；
> 本文件 = **可迁移的原则 / 技巧 / 指南**；`文档维护日志.md` = 文档版本账。

## 治理类（2026-10-24 与负责人商定）

### G1 全权 ≠ 无人驾驶
执行与文档全权交给 Agent，但 **push / tag / 不可逆操作必须逐次授权**。
**判据**：一个动作能否靠 `git` / 重跑找回 —— 找不回就报批。
**反例**：推 tag 上 public 不可逆；`export --all` 批量建笔记会让 vault 不可逆膨胀。

### G2 花钱路径先列后做
任何新增 LLM 调用点 / Actions / 第三方 API，开工前给出「单次 / 日 / 月 / 年」估算，
上线后**实测回填**。`off` 档必须恒 0。
**判据**：报告里出现"预计花费"却没有"实际花费"，视为未完成。

### G3 预算卡「调用前」，不卡「生成中」
**原则**：钱不够 = 少做或进队列，**不是降低单篇质量**。闸门在发起调用前预估并拦截，
绝不中途截断生成。
**反例**：为了不超 max_tokens 而让模型回显摘要、砍掉六段之一 —— 那是质量事故，不是省钱。

### G4 交接文档要能「盲测」
阶段交接文档质量门槛：**新 Agent 只读 CODEBUDDY.md + handoff 能独立跑通并说出风险**。
写法：写完后自己不看对话、照文档走一遍，走不通就是不合格。

## 成本类

### C1 成本失控是「叠乘」，不是「单价」
```
500 篇/天 × 50k 全文 × 1 元/M = 25 元/天 ≈ 9,000 元/年
```
单看单价不贵，一次「图省事对全量做深度分析」就是 60 倍。
**原则**：闸门必须同时卡「篇数 × 上下文长度 × 调用次数」，缺一不可。

### C2 单价模型要三档，单一数字必错
计费是「输入命中 / 输入未命中 / 输出」三档，输出单价常是输入的 2 倍。
**反例**：`config/default.yaml` 原 `price_fast_cny_per_1m: 1.0` 单一数字，无论怎么填都系统性低估。

## 工程类

### E1 死配置要么接消费者，要么写明「消费方在哪个阶段」
**反例**：`similarity_strong_weight`（0.30）无人读 —— 留下"看起来已实现"的假象。
`budget` 块同理。**判据**：每个配置项在源码里 grep 得到消费方，否则视为未完成。

### E2 测试绿 ≠ 功能完整
206 测试全绿、`export --check` 0 变更，仍漏了三个洞（无笔记边不显示相似度 /
`--dry-run` 把存量报成新增 / 死配置）。
**原则**：推送前按任务卡 DoD 与「可解释性 / 幂等 / 降级」三条逐一对，不看 pytest 数。

### E3 断言打在「真实结构」，不打在「看起来对」的东西上
**反例**：`assert "★" in output` 命中脚注说明文字 → 恒真（本项目已三次踩中，红线 18）。
**判据**：写断言前先问「这条断言在什么情况下恒真 / 恒假」。

## 数据类

### D1 能用实测替代推断的，不要推
引用命中率推了三轮都错，实测一次即推翻（0.0095% ≈ 零）。
**原则**：体积 / 关联 / 命中率这类量级判断，先实测，不靠推断。拿不到真值就 `skip`，不伪造。

★ **反例（2026-10-25）**：曾据「ar5iv 是 arXiv HTML 镜像」推断它可作正文回退源；
实测发现它对**有 HTML 和没有 HTML 的论文都只返回约 5k 字符的 arXiv 摘要页**（导航 + 主题分类），
不是正文。若照推断实现，prompt 会误以为有全文，比返回 `None` 更糟。
⇒ **外部源的能力先实测再接线**，尤其是「回退源」——错的回退会伪装成真数据。

## 输出规范类（2026-10-24 与负责人商定）

### O1 两张进度表（每个大小阶段都遵循）

每次阶段输出固定两张表，让负责人一眼看清「全局在哪」与「当前阶段到哪」：

**表 1 · 项目整体进度**（所有里程碑，当前 + 前序 + 后序，标注状态）：

| 阶段 | 内容 | 状态 |
|---|---|---|
| L0-A/B/C | 骨架 / DB / 导出器 | ✅ 完成 |
| L1-0 | vault 迁出 | ✅ 完成 |
| L1-A/B/C | S2 / signals / 耦合+相似 | ✅ 完成 |
| **L2** | Actions 自动化 + 每日报告 | ✅ 完成 |
| **L2-C** | Daily Note（`40-日志/`） | ✅ 完成 |
| L3a / L3b | LLM 增强 / 定级+深度分析 | ✅ 完成 |
| L4 / L5 | 推演 / 呈现形态 | ⬜ 未开始 |

**表 2 · 当前大阶段分级进展**（与项目文档/任务卡对齐）：

| 子阶段 | 内容 | 状态 | 验证证据 |
|---|---|---|---|
| L2-前置 | 模型名迁移 + 预算闸门 | ✅ 完成 | 测试全过、真实运行成功 |
| L2-A | 每日报告产物 | ✅ 完成 | 测试全过、实跑产出正常 |
| L2-B | daily.yml + commit 机制 | ✅ 完成 | 实跑全链路通过 |
| L2-C | Daily Note（`40-日志/`） | ✅ 完成 | 测试全过、用户区不被覆盖、连续两次导出无 diff |

★「验证证据」列用**通俗结果**表述（「测试全过」「真实运行成功」），
不用代码覆盖率等技术数字 —— 让负责人一眼看懂，不暴露实现细节。

**待决策的固定子格式**：`决策项 → 理由 → 影响 → 利弊 → 推荐`，
每条决策都按这个顺序写，负责人不用在长文里自己提炼。

**Why**：项目跨多阶段、每阶段又分子阶段，纯文字叙述负责人要自己拼进度。
**How to apply**：阶段名、子阶段划分、状态标记（✅/🔄/⬜）与 `执行手册.md` §5、`设计方案.md` §8 对齐，不另造口径。

### O2 阶段收尾 = 下一阶段 handoff 就位（clear/init 前置）

**规则**：每个大阶段宣布完成前，必须**新建** `docs/handoff/L{下一阶段}-开工.md`；
当前阶段文件标「已归档」并指向新文件。下一阶段 Agent 只靠它恢复上下文。

**Why**：每个大阶段结束都会 **clear + init**，上下文归零；handoff 缺失 = 下阶段在无上下文下开工。
2026-10-25 实际发生过：把 L4 内容写进 `L3-开工.md`，文件名仍锚定 L3，靠负责人提醒才发现。

**How to apply**：
- 收尾清单显式包含「新建下一阶段 handoff」+「当前阶段归档」；
- 跑 `uv run pytest tests/test_docs_consistency.py -q`（机械校验下一阶段 handoff 存在且未归档）；
- ★ **不要只改现有 handoff 的内容** —— 文件按阶段命名，**内容更新 ≠ 交接完成**。
