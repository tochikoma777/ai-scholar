## 0. TLDR（3 分钟版）

> **★ v1.1 追加核心能力：论文深度分析**（§5.5）——项目定位从"关联工具"
> 升级为"**学习工具**"。
> **★ v1.3 修正定位表述**：四段（采集→关联→推演→沉淀）是**建库**，
> 论文深度分析是**读懂单篇**。两者**并列**，不是从属——缺一个都不成立。

### 0.1 项目定位

**AI 领域文献的自动采集、关联分析、趋势推演与知识库沉淀**，
外加**论文深度分析**（把单篇读懂并掌握），输出为 **Obsidian 知识库**。

一句话：**不只是把论文搬进知识库，而是让每篇论文知道"它和谁有关、为什么重要、往哪走"。**

★ **核心判据**：导出的东西**能不能直接喂给别的 AI 工具**。
所以导出物是**合成文档**（条目元信息 + why + 我的笔记），**不是条目列表**。

★ **动机**："没看完的东西以后还能用"。

### 0.2 与 aipulse 的关系（重要）

本项目**不是从零开始**——它是 aipulse 的姊妹项目，**复用其架构决策与踩坑经验**。

| 维度 | aipulse | AI Scholar |
|---|---|---|
| 核心 | 热点聚合 + 预言 | **文献关联 + 知识沉淀** |
| 主要源 | GitHub Trending / HN / Reddit | **arXiv / HF / Semantic Scholar** |
| 时间尺度 | 24 小时滚动窗口 | **长期累积** |
| 产出 | 每日日报 | **Obsidian 知识库（累积）** |
| 幂等难点 | 中（快照型源无稳定 id） | **低**（arXiv ID/DOI 天然稳定）✅ |

**★ 直接复用（不要重新设计）**：三档运行模式、三级降级阶梯、静默失败治理、防幻觉双层防护、结果持久化、环境分级、单源失败隔离、文档维护规范。

### 0.3 技术栈

| 层 | 选型 |
|---|---|
| 语言/包管理 | Python 3.11+ · **uv** |
| 存储 | **SQLite + SQLModel（基于 SQLAlchemy）+ alembic**（元数据库）+ **Markdown 文件**（知识库本体） |
| HTTP | **httpx**（统一走自研 `HttpClient`） |
| LLM | **httpx 直连 DeepSeek，不用 SDK** |
| 关联计算 | 引用图 + TF-IDF/embedding 相似度（**零 LLM**） |
| 输出 | **Markdown + YAML frontmatter + wikilink**（纯文本，不依赖 Obsidian 插件） |
| CLI | Typer |
| 自动化 | GitHub Actions |
| 质量 | pytest + respx + ruff + **mypy strict** |

★ **必须留 `Exporter` 抽象**（C1.3）——即使当前只有 Obsidian 一个实现。

### 0.4 里程碑

```
L0 骨架+探测+采集+导出  →  L1 关联分析  →  L2 Actions自动化(★提前)
                       →  L3 LLM增强+定级+深度分析  →  L4 推演与演化
                       →  L5 呈现形态（L5a 静态 HTML ✅ / L5b 交互看板 ✅）
                       →  L6 运营修复与维护（进行中）
```

**★ L2 自动化提前的理由**（源自 aipulse 教训）：**知识库的价值完全靠时间积累**。

★ **L5 呈现形态（v1.9 更新）**：
- L0–L4 **不引入** `fastapi` / `uvicorn`
- **L5a 已实现并验收**：`ai-scholar site` 静态 HTML 单文件（Exporter 第二实现，零新增依赖），
  只读 public 数据、不读 vault、分项分不合成总分、`--check` 逐字节幂等
- **L5b**：交互式 Web 看板（单文件 + 原生 JS + 内嵌 JSON，零后端），L5a 验收后开工

★ **C2 第一杠杆**：`off` 档**零配置可用**——判据是"一个人能在 5 分钟内看到自己的第一个 vault 吗？"

### 0.5 三个核心设计（全文最重要）

| # | 设计 | 一句话 |
|---|---|---|
| 1 | **关联分层：显式 > 语义 > 实体 > 时序** | 能用数据算的绝不用 LLM |
| 2 | **★ 新论文的引用数据必然缺失，需要"补齐队列"** | 新论文只有 references，citations 要等几周 |
| 3 | **★ 推演必须区分"可证伪"与"观点"** | 不可证伪的洞察不许进记分板 |

## 1. 需求与目标

### 1.1 原始需求

> AI 领域文献分析、关联和知识库沉淀归档。每日自动收集 AI 领域热点文献；
> 不仅能收集整理，还能进行分析，与领域内其他文献进行推演或关联，
> 做影响分析和未来发展趋势推演，输出到知识库沉淀归档（Obsidian）。

**★ 项目负责人追加（v1.1）**：对采集的论文进行分析解读，
以供了解、学习、掌握论文——**这是核心诉求的落地点**（§5.5）。

### 1.2 需求拆解

| 需求 | 本项目实现 | 关键约束 |
|---|---|---|
| 每日自动收集 | arXiv + HF Daily Papers + Semantic Scholar | **索引滞后**，见 §3.3 |
| 整理 | 去重、打分、主题聚类、元数据规范化 | 身份用 arXiv ID/DOI |
| **关联** | 引用图 + 语义相似 + 实体共现 + 时序演化 | ★ 核心差异化，见 §5 |
| **分析** | 方法提取、贡献定位、局限性 | LLM，仅对高价值论文 |
| **★ 深度分析** | 六段结构 + 三句半 + 背景透镜 | 见 §5.5，注意力预算内 |
| **影响分析** | 被引用增长、方法被采纳程度 | 需时间积累 |
| **趋势推演** | 主题演化链、方向冷热、未来预判 | ★ 必须区分可证伪性，见 §7 |
| **知识库沉淀** | Obsidian Markdown + wikilink | 见 §6 |

### 1.3 明确不做（YAGNI）

- ❌ **著作（书）**：周期过长，与"每日"节奏不匹配
- ★ **全文 PDF 存储**（v1.3 修正）：**永不入库**。
  仅在**深度分析触发时**临时抓取正文，**抓完即弃**（临时目录、`persist` 永远 false、绝不 commit）。
  ⚠️ **若有人提议"存下来省得重复抓"，回绝**——跨过去合规性质就变了。
- ❌ **向量数据库**：论文量级（万级）用 TF-IDF + SQLite 足够
- ★ **交互式 Web 看板**（v1.10 更新）：**已交付** —— L5b「单文件 + 原生 JS +
  内嵌 JSON」，零后端；筛选 / 排序 / 搜索，仍不读 vault、不渲染个人笔记。
  只有出现多用户 / 实时 / 权限硬需求时才评估 server / SPA。
- ❌ **中文文献源**：当前基本空白（知网无开放 API）。**明确记录为已知局限**，不做虚假覆盖

## 2. 数据源

★ **三类分清**（v1.3 新增，避免混淆）：

| 类 | 源 | 作用 | 产生新条目？ |
|---|---|---|---|
| **采集源** | arXiv API、HF Daily Papers | 发现新论文 | ✅ |
| **增强源** | **S2**、**OpenReview** | 补全已有条目 | ❌ |
| 推荐源 | S2 recommendations（种子 = 已读） | L4+ 才做 | ⚠️ |

### 2.1 主源

| 源 | 提供什么 | 唯一性 | 分级 |
|---|---|---|---|
| **arXiv API** | 论文元数据 + 摘要 + 分类 | **学术一手源**，不可替代 | always |
| **HF Daily Papers** | 论文的**社区认可度** | ★ v1.3 修正：见 2.1.1 | always |
| **Semantic Scholar (S2) API** | **★ 引用关系**（references/citations）+ 影响力指标 | **★ 唯一提供引用图的源**，本项目的地基 | always |

> S2 无 key 时速率限制严（共享池，忙时限流）。**建议申请免费 key**，
> 但**必须能无 key 降级运行**（红线）。

#### 2.1.1 ★ HF 的真实角色（v1.3 新增，来自实测）

**实测发现（2026-10-21，1 天窗口）：HF 与 arXiv 当天集合的【交集 = 0】** —— HF 上榜论文滞后 2~4 天提交，
不在 arXiv 当天集合里，但 50/50 能在 arXiv 全库回查到。

> ★ **v1.3.1 修正（2026-10-22，L0-B 实测）**：上述「交集 = 0」是 **1 天窗口的假象**。
> L0-B 用 **2 天窗口**采集时，HF 的 42 条里有 **11 条（26%）命中了 arXiv 已入库条目**。
> ⇒ 按 §3.3 启用 **7 天回看窗口**后，HF 论文会大量解析到其 arXiv 原始条目，
> **跨源去重率显著上升**。⇒ §12 的「并集 ≈ 515」是**上界**，实际 `N_enter` 更低。

⇒ HF **不提供"独有论文"**（arXiv 回看窗口会补上），它的真价值是：
1. **提前 2~4 天发现**
2. **社区热度信号**

⇒ **HF 得分应写进条目作热度/排序信号，而非只当采集源**。

#### 2.1.2 ★ S2 端点硬约束（v1.3 新增）

```
POST https://api.semanticscholar.org/graph/v1/paper/batch?fields=...
  Header: x-api-key（大小写敏感）  Body: {"ids": [...]}  上限 500 ids/次
★ 全程 batch，【禁止逐篇 GET】
```
每天 100~500 篇新论文 = **1 次请求**，无论按哪个限速口径都绰绰有余。

### 2.2 可选源（后期）

- Papers with Code（SOTA 追踪、代码可用性）——**已并入 HF，不单列**
- ★ **OpenReview**（v1.3 更新）：**L1 可选增强**。
  价值 = 提供「是否已被顶会接收」这个**比等引用数快得多**的强信号，正好打在延迟定级的痛点上
  - 公开 venue 免认证；★ 社区坑：**invitation 写错不报错、只返回空列表** → 必须有断言非空的单测
  - ★ **国内访问不稳定是已知预期** → 环境分级 `optional_enrich`：
    失败只写 warning、字段留空、**不影响退出码**，不作为 bug 排查
- 作者主页/RSS（特定学者追踪）

★ **加源一次只加一个**（通用原则：一次只做一件事）。

### 2.3 中文源

**当前基本空白**（知网无开放 API）。**明确记录为已知局限**，不做虚假覆盖。

## 3. 关键设计决策

### 3.1 ★ 双存储：SQLite（元数据）+ Markdown（知识库）

| | SQLite | Markdown 文件 |
|---|---|---|
| 存什么 | 论文元数据、关联关系、评分、signal 快照、运行状态 | **知识库本体**（给人看的） |
| 谁写 | 采集/分析链路 | **导出器**（单向：DB → 文件） |
| 能否手改 | 否 | **能**（用户可以在 Obsidian 里加笔记） |

**★ 关键约束：Markdown 是 DB 的"物化视图"，单向生成。**

**解决方案（必须实现）**：

1. 每篇文献页面用**标记块**分隔生成区与用户区：
   ```markdown
   <!-- BEGIN GENERATED -->
   （生成内容，重新导出会覆盖）
   <!-- END GENERATED -->

   ## 我的笔记
   （用户内容，永不覆盖）
   ```
2. **只替换标记块之间的内容**，用户区原样保留
3. 用户笔记如需持久化到 DB，提供 `import` 命令反向同步（**可选，后期**）

> **这是本项目最重要的工程约束之一**：不实现标记块，用户的所有笔记会在某次重新导出时被清空。

### 3.2 ★ 文献身份与幂等

| 项 | 设计 |
|---|---|
| 主键 | `arXiv:{id}` 或 `DOI:{doi}`，**归一化后作为稳定 id** |
| 文件 id | 同主键（清洗后作为文件名） |
| 重复采集 | **upsert 幂等**，同一篇论文反复出现只更新不新增 |
| 合并 | arXiv 与 HF 同一篇论文按 arXiv ID 合并，**HF 只补充热度字段** |

**对比 aipulse 的优势**：文献有天然稳定 id。
但要**避免把 HF 的点赞数当作身份依据**。

#### 3.2.1 三级去重（明确定义）

| 级 | 内容 |
|---|---|
| **一级 身份** | 主键归一化（大小写、版本号 `v2` 后缀、DOI 前缀统一）→ upsert 幂等 |
| **二级 跨源** | arXiv 与 HF 同一篇按 arXiv ID 合并，HF 只补热度 |
| **三级 跨版本** | 预印本 ↔ 正式版用 `paper_aliases` 表归一到 `canonical_id`（**别名不产生新条目**） |

#### 3.2.2 ★ 结果持久化的 hash 必须排除易变字段

**★ 硬约束**：`content_hash` **只含影响分析结论的字段**
（**标题 / 摘要 / 作者 / venue**），**必须排除引用数、热度、点赞数**——它们每天都在变。

否则：引用数每天变 → hash 每天变 → **持久化形同虚设，成本线性增长**。

> 这与「幂等导出 vs 文件内时间戳」是同一类错误：
> **把"会变的量"当成了"内容是否变化"的依据。**

**★ 关键区分：不进 hash ≠ 不存储。**

| 字段 | 性质 | 去哪 |
|---|---|---|
| title + abstract + authors + venue | **内容身份**（写完就不再变） | ✅ 进 hash |
| citation_count / 热度 / score | **观测值**（每天都在变） | ❌ 不进 hash，但**照存** → `signals` 表按天一行 |

> 类比：**身份证号不随体重变**；体重每天称，记在体检表（`signals`）里。

★ **两个实现陷阱（v1.3 新增）**：
1. **作者字符串跨源不一致**（`J. Doe` vs `John Doe`）会算出两个 hash →
   hash 前必须归一化（小写、去标点、`姓+名首字母`）
2. **预印本 venue 为空、正式版变成 "NeurIPS 2026"** → hash 变 → 由 `paper_aliases` 兜住（三级去重）

**★ 易变字段变化应该触发"重新定级"，不是"重新深度分析"。**

★ **默认绝不重做**；仅 4 种例外（显式指定 / prompt 版本升级 / 内容 hash 变 / 用户手动），
且需**显式触发**。**我的笔记永不重做、永不覆盖**。

### 3.3 ★ 时间语义（直接复用 aipulse 三态，但有新难点）

| 语义 | 依据 | 适用 |
|---|---|---|
| `event` | `published_at` | HF Daily Papers（当日上榜，时间准确） |
| `discovery` | `first_seen_at` | **arXiv（索引滞后 3–7 天）** |

★ **v1.3.1 新增：回看窗口（lookback window）默认 7 天**
- 配置项：`arxiv.lookback_days`；CLI `--days` 默认取它
- 理由：① 本表载明滞后 **3–7 天**，取上限才安全
  ② 实测：同一日期（10-20）在 10-21 探测 362、10-22 探测 465 —— **1 天后仍在增长**
  ③ 加宽代价极低（多约 6 次请求 / 约 18 秒），收益是**不漏采**
- ★ 幂等由 `first_seen` append-only + upsert 兜住：重复扫**不产生重复条目**
- ★ 连带收益：窗口加宽后，HF（滞后 2~4 天）能解析到其 arXiv 原始条目 → **跨源去重率上升**
- ⚠️ **L1 待实测**：某日期的条数**几天后收敛**，据此回调 `lookback_days`

★ **v1.3 补充（实测）**：`submittedDate` 框定某天的 total **会随索引补全增长**
（2026-10-20 这天：10-21 探测 362，10-22 探测 465）。
⇒ **单日 N 是下界**，体积估算必须标「**区间 + 探测日**」。

**新难点：引用数据的滞后不是"几天"，而是"几周"。**

- 新论文入库时，`references`（它引用了谁）**立即可得**
- 但 `citations`（谁引用了它）**几乎必然为空**

**★ 解决方案：补齐队列（enrichment queue）**

```
新论文入库 → 进 pending_enrich 队列
             ↓（每天批处理时尝试）
    查询 S2 引用关系 → 成功则出队 + 重建关联
                     → 失败（404/限流）则保留，下次再试
             ↓
    超过 N 天仍失败 → 标记 stale，不再重试（记录原因）
```

**为什么必须这样**：如果只在入库当天查一次引用，**所有论文的关联图都是空的**。

★ **v1.3 补充：出边与入边要分开看**（这决定冷启动主线）
- **出边（A 引用谁）**：新论文当天就有 → **立刻可建** ✅
- **入边（谁引用 A）**：新论文必然空，但**可由每天新增论文的出边反向生成** ✅
- S2 `/citations` 只用于**回填历史缺口**，是补齐队列的活，**不是冷启动主线**

### 3.4 三档运行模式

★ **v1.3 修正档位命名**：`off` / **`fast`** / **`strong`**（原稿写 `hybrid`/`full`，与已实现代码不一致）

| 档 | LLM | 产出 |
|---|---|---|
| `off` | **零调用** | 元数据 + 摘要 + **零 LLM 关联**（引用图+语义相似） |
| `fast` | 高价值论文增强 | + 一句话 + 为什么重要 + 方法标签；**定级**也在此档 |
| `strong` | 追加深度分析 | + 六段深度分析 + 三句半 + 背景透镜 |

**★ off 档必须能完整跑通**——这是 aipulse 验证过的最重要设计，
也是 C2「5 分钟第一个 vault」的基础。
**注意**：off 档下**关联分析依然可用**（引用图 + 语义相似都是纯算法）。

★ **未配 api_key ⇒ 自动降级 `off` 且不报错**（退出码 0）。

### 3.5 三级降级阶梯（复用，无改动）

```
json_schema → json_object → plain
```
降级状态按 **(model, format)** 记忆，不能全局布尔。

### 3.6 成本控制

**本项目 LLM 成本高于 aipulse**（每篇论文都要处理），必须分层：

| 层级 | 范围 | LLM |
|---|---|---|
| 全量 | 所有新论文 | **零**（存元数据+摘要） |
| 高价值 | 打分 Top N（默认 20） | 一句话 + 为什么重要 |
| 强关联对 | 相似度 > 阈值 的前 M 对 | 关联解读 |
| ★ 深度分析 | **注意力预算**（每周 5 篇） | strong，六段 + 三句半 + 透镜 |

**三条硬约束**（源自 aipulse 教训）：
1. **结果必须持久化**（content_hash + TTL，hash 排除易变字段见 §3.2.2）
2. **输出必须紧凑**——只返回 `id + 字段`，**不回显标题/摘要**（回显会撞 max_tokens）
3. 中文概述只对非中文条目生成

### 3.7 ★ 数据落点与信号采样（v1.3 新增，定案 C′）

#### 3.7.1 数据落点

| 数据 | 可再生？ | 落点 | 入库 |
|---|---|---|---|
| 论文元数据、关联边 | ✅ 重采即回 | `data/ai_scholar.db`（**可丢弃缓存**） | ✗ |
| **`first_seen_at`** | ❌ | `data/first_seen.jsonl` | ✓ public |
| **signals 时序快照** | ❌ | `data/signals/YYYY-MM.jsonl` | ✓ public |
| 每日报告 md + json | ✅ | `data/reports/YYYY-MM-DD.{md,json}` | ✓ public |
| 用户笔记 | ❌ | **独立 private vault 仓库** | ✗ |
| 论文正文 / 全文 | — | **永不入库** | ❌ 绝对禁止 |

★ **vault 与代码仓库物理隔离**。Actions **只 commit public 仓库**；
vault 由本地 `export` 写入。任何"让 Actions 写 private vault"的设计都已被否掉。

★ **不落 vault 的理由**：跨仓写权限（deploy key/PAT + fork PR 风险）是已否掉的设计；
而 ~11 MB/年 对 public 完全可接受。

★ **`first_seen_at` 保留的唯一理由 = 不可再生**。
（曾以"重采很贵"作论据，该论据已作废——S2 batch 一次 500 ids，重采极廉价。）

**★ `paper_references` 表（v1.7 新增，只落 db）**

```
paper_references(paper_id, ref_external_id)      -- 只存外部 ID，不存元数据
≈18.6 条/篇 × 18.8 万篇/年 = 350 万行/年 ≈ 143 MB/年
```

| 项 | 规则 |
|---|---|
| 落点 | **只落 db（可丢弃缓存）**，不进 public、不进 JSONL |
| 用途 | 文献耦合计算（§5.1c） |
| ★ 必要性 | 引用边命中率仅 0.0095%，**不存引用列表就没有可用的引用类关联** |

#### 3.7.2 ★ 采样状态机（持久状态，不是每日重算）

```
observed_pending   预筛通过 & 未定级
  ├ 频率：【每月】全程
  └ 退出：a) 已定级 ⇒ observed_tracked
          b) first_seen+90 天仍未成熟 ⇒ 标 low_impact ⇒ dormant

observed_tracked   已定级 / 已深度分析
  └ 频率：第 1 年【每月】，之后【每季度】，保留 3 年

dormant            ★ 不常规观测
  └ 复活：published_at + 180 天【单点采样一次】
     条件：【仅】citation_count ≥ min_citations
           ★ age 是"何时采"，不参与"是否复活"
     次数：★ 最多一次，再次不达标永久 dormant

observed_sample    留样集（被预筛淘汰 × r=0.2），与 pending 分离
  └ 频率：【每季度】，保留 365 天；用途【仅校准】，不驱动定级

快路径    进入时 published_at ≥ 180 天 ⇒ 跳过 pending 直接定级
时钟      ★ 成熟度 = published_at（唯一）；观测窗口 = first_seen（唯一）
幂等      PRIMARY KEY (paper_id, observed_at)
```

★ **体积公式**：总量 = `N × p + N × (1-p) × r`
- `r = 0.2` 是**淘汰集抽样留存率**，**不是总体放行率**
- `p` = 预筛通过率，**必测**，是体积最大杠杆
- 估算：N≈515/天、p=0.8 → **≈110 MB/年**（含 first_seen）

★ **安全阀（体积超标时的降级顺序）**：
① 已定级集月→季 ② 复活检查只留 +180 一个点 ③ pending 段降频 ④ 调小 `r`（最大杠杆）

## 4. 评分与筛选

### 4.1 为什么需要打分

每天新论文可能几十到上百篇。**不可能全部精读**——打分的目的是**帮你果断放弃大部分**。

### 4.2 评分维度（权重全部外置到 yaml）

| 维度 | 说明 |
|---|---|
| **社区热度** | HF 点赞/讨论数（对数归一化） |
| **来源强度** | 是否同时出现在 arXiv + HF（跨源加成） |
| **作者/机构** | 已知高产作者或顶级机构（可选，需实体词典） |
| **主题相关度** | 与关注清单（watchlist）的匹配度 |
| **引用势能** | 已有 citations 的增速（**老论文才有**） |

**★ 与 aipulse 的关键差异**：aipulse 用"24 小时热度"，本项目**热度意义下降、价值意义上升**。

> **★ 所有新论文都进知识库（db），打分只决定"当天优先看什么"和页面上的推荐标记。**

### 4.2.1 ★ watchlist 是意图层，不是入口过滤器（v1.3 新增）

**★ 硬约束**：watchlist **只做三件事**——① 打 ★ 标记 ② 触发通道 A 深度分析 ③ 参与排序。
它**永远不是入口过滤器，不决定论文是否入库**。

理由（任一条成立即须遵守）：
1. 领域过滤 = cs.AI/CL/LG，**已在 arXiv 查询时用 `cat:` 施加**
2. 若只有命中 watchlist 的才入库 ⇒ 预筛**失去对象**、关联图只含我关心的方向
   ⇒ **背叛项目动机"没看完的东西以后还能用"**
3. `N_enter` 会随 `watchlist.local.yaml` 漂移，不可复现

> ⚠️ **本项目已犯两次同类错误**（另一次是把定级硬约束搬进 `exclude_penalty`）：
> **把上层（意图/定级）规则搬到下层（采集/入口）**。请特别警惕这条边界。

### 4.2.2 watchlist 配置（v1.3 新增）

```
config/watchlist.yaml        提交的【通用示例】，只含中立主题（入仓）
config/watchlist.local.yaml  个人真实兴趣（.gitignore 排除）
加载顺序：local 深合并覆盖 default
```

- 匹配：title 或 abstract，word-boundary，大小写不敏感
- 命中【布尔】→ 触发；命中【分】= **Σ(命中组权重)**，同组多次只计一次 → **仅排序**
- ★ **不新增词级权重字段**——组权重已能承担
- ★ **`exclude_penalty` 不实现**——它属定级层硬约束，搬到意图匹配层是层次混淆；
  且顶会好论文摘要写 SOTA 极普遍，降权会系统性误杀
- ★ **不入库的理由是"配置洁癖"，不是隐私**：
  别人 clone 下来不该带着你的兴趣清单（且你每次改都要 commit，噪音）。
  **每日报告照常公开含 ★**。

## 5. ★ 关联分析（核心差异化）

### 5.1 四层关联

**原则：能用数据算的绝不用 LLM。**

| 层 | 依据 | 成本 | 可靠性 |
|---|---|---|---|
| **1. 显式引用** | S2 references/citations | 零 LLM | **最高**（事实） |
| **2. 语义相似** | TF-IDF / embedding 余弦 | 零 LLM | 高 |
| **3. 实体共现** | 共享方法/数据集/基准（词典+正则） | 零 LLM | 中 |
| **4. 时序演化** | 同主题内的先后关系 | **需 LLM**（仅对强关联） | 中 |

**★ 关键：前三层零 LLM，off 档完全可用。** 只有第四层需要模型。

#### 5.1b ★ 引用关联的冷启动稀疏性（v1.5 新增，修正 D2 的论证漏洞）

**D2 曾论证**："出边（A 引用谁）新论文当天就有 → 立刻可建；入边由出边反向生成
→ 不需要等 S2 `/citations`。" —— **这个论证有一个未言明的前提：被引用的论文也在库里。**

**实际情况**：新论文引用的绝大多数是**库外的老论文**（我们只从某天开始采集，
库里没有历史积累）。若被引目标不在库内，**出边同样建不了**。

⇒ **冷启动期（前几个月）引用关联必然稀疏，这是预期不是 bug。**

**★ L1-A 实测（v1.6，2026-10-24）**：

```
首次 enrich（库内 351 篇）：31,542 条 references → 命中库内    0 条
扩大到 2,174 篇后        ：31,542 条 references → 命中库内    3 条
                                              命中率 0.0095%
```

| 判据 | 结论 |
|---|---|
| 是 bug 吗？ | ❌ 不是。随机期望约 6.9 条，实测 3 条同数量级 |
| 比 §5.1b 写的更严重吗？ | ✅ 是。原写"稀疏"，实际**接近零** |
| ★ 更糟的一层 | §5.6 定 vault 只给 ~500 篇建笔记 ⇒ 即使全库命中率升到 1%，**这 500 篇之间的引用边仍约等于 0**（又小 460 倍） |

⇒ **引用边永远不会是本项目的主要关联机制** ⇒ 解法见 **§5.1c 文献耦合**。

**三条应对（已定）**：
1. **不回采被引论文** —— 每篇引约 30 条，515 篇/天 ⇒ 若按需补全会引入
   ≈1.5 万条/天（**564 万行/年**），库会失控
2. **只存库内目标的边** —— 外部目标只计入 `refs_count`，**不写 `paper_links`**
   （否则产生无法渲染的"幽灵条目"）
3. ★ **真正的冷启动主线是语义相似**（§5.2，TF-IDF 零依赖，当天即可算）
   —— 它不依赖引用数据，也不依赖被引论文在库内

**DoD 影响**：L1-A 验收时**不得**因"关联边很少"判定失败；
应改为断言"边的关系方向正确 + 库内目标命中率合理"。

#### 5.1c ★ 文献耦合（v1.7 定案，冷启动的真正主线之一）

**问题**：L1-A 实测 —— 31,542 条 references 只命中库内 **3 条**（**0.0095%**）。
且 §5.6 让问题更严重：即使库涨到 23 万篇、命中率升到 1%，**笔记子集（~500 篇）
之间的引用边仍约等于 0**（又小 460 倍）。
⇒ **引用边永远不会是本项目的主要关联机制。**

**解法：文献耦合（bibliographic coupling）**

```
现在：A 引用 C → 要 C 在库内才建边 → 0.01%
耦合：A 和 B 引用了【同一批】文献 → A、B 相关
      ★ 完全不需要 C 在库内 —— 只比较两人的参考文献【列表】
```

| 关联类型 | 需要什么 | 冷启动 |
|---|---|---|
| 引用边 | 被引论文在库内 | ❌ 0.01% |
| 共被引 | 施引论文在库内 | ❌ 更差 |
| **文献耦合** | **只需两份参考文献列表** | ✅ **当天可用** |

**实现**：`paper_references`（§3.7.1）按 `ref_external_id` 倒排，
同 ref 的论文两两计 1；按 Jaccard 或共现数归一化，取 Top-N。
**★ 零 LLM、零额外网络请求** —— 数据已在 L1-A 采到，只是当时写边后就扔了。

### 5.2 语义相似的实现

- 文本：标题 ×2 + 摘要 ×1（权重外置）
- ★ 分词：**英文分词 + 英文停用词**（v1.3 修正：原稿"复用 jieba"——
  jieba 是**中文**分词器，而本项目文献源是**英文**，中文源明确不覆盖）
- 向量：TF-IDF（万级论文足够；embedding **默认关闭**，但留 `SimilarityProvider` 抽象）
- 阈值：进池 0.15，强关联 0.30（**可配**）
- 每个文档保留 Top-K 相似（默认 10，可配）

**★ 计算量控制**：增量计算——只算**新论文 vs 存量**的相似度，不做全量重算。

### 5.3 ★ 关联的双向性与回写难题

**问题**：A 关联 B，则 B 的页面也要显示 A。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 全量重建 | 每次重新生成所有页面 | 简单、永远一致 | 论文多了会慢 |
| B. 增量回写 | 只重建受影响的页面 | 快 | 需要维护反向索引 |
| C. Dataview 动态查询 | 关联由 Obsidian 查询时计算 | 无回写问题 | 依赖插件 |

**★ 推荐：默认 B（增量回写 + 反向索引），可选 C。**

理由：论文量级（万级）下 B 完全可行，且**不依赖任何 Obsidian 插件**——
纯 Markdown 兼容性更好；C 要求用户装 Dataview，违背"自包含 Markdown"原则。
A 作为**兜底**（`rebuild --all`）。

**实现要点**：维护 `paper_links` 表（source, target, type, score），双向存储。

### 5.4 关联的可解释性

**★ 每条关联必须能说明"为什么关联"**：

| 类型 | 显示 |
|---|---|
| 引用 | `引用了 [[B]]`（事实，无需解释） |
| 语义相似 | `相似 0.42` + 共享关键词 |
| 实体共现 | `共享：RLHF / HH-RLHF 数据集` |
| 时序演化 | `（LLM 判断）B 在 A 基础上改进了 X` |

> **不可解释的关联不要用**——用户无法判断该不该点进去，等于噪音。

## 5.5 ★ 论文深度分析（核心能力）

> 需求来源：项目负责人追加——"对采集的论文进行分析总结并输出报告，
> 以供我了解、学习、掌握论文"。**这是用户核心诉求的落地点。**

### 5.5.0 ★ 输出结构总览（v1.3 新增）

一篇深度分析过的论文，其 vault 笔记生成区自上而下为：

```
【TL;DR · 三句半】≤400 字（坐标/痛点/手术/疗效/代价）
【六段结构】总体介绍/核心思想/技术路线/主要贡献/历史地位(条件式)/局限性
【背景透镜 · 五问】瓶颈资源/换了什么/代价落哪/何时失效/能否反向迁移
【客观信号 vs LLM 判断】分列，不给综合分
```

★ **三句半与六段必须在【同一次 LLM 调用】产出**——避免互相矛盾、省一次调用。

### 5.5.1 六段结构

| 段 | 内容 | 是否 LLM |
|---|---|---|
| 总体介绍 | 简短精炼，1-2 句说清它是什么、解决什么问题 | ✅ |
| 核心思想 | 它到底提出了什么（**不是摘要复述**） | ✅ |
| 技术路线与结构特点 | 方法怎么组织的 | ✅ |
| 主要贡献 | 相对既有工作，它多了什么 | ✅ |
| **历史地位** | **条件式**：有施引数据才输出并附证据；无则标注「待观察：发表 N 天，被引 M 次」 | ⚠️ 条件 |
| 局限与不足 | 作者承认的 + 分析推断的，**分别标注** | ✅ |

> ★ v1.3：修正原稿表格中「主要贡献」重复两行的笔误。

**★ 历史地位是条件式输出**：
- **有施引数据**（被引 ≥ 阈值、发表 ≥ 12-18 个月）→ ✅ 输出判断，**须附证据**
- **数据不足**（新论文）→ 不输出 + 标注「待观察：发表 N 天，被引 M 次」

> 最初写的是"一律不做"，**项目负责人修正为条件式**——这是对的。
> 教训：**条件式降级 > 一刀切砍功能**。

★ **prompt 硬约束**：禁止推测影响力与历史地位；无数据即留空，
**不得以"可能/有望"填充**。另设「初期信号」字段（**纯数据、非 LLM 判断**）始终输出。

### 5.5.1b ★ 三句半（v1.3 新增）

仅仅输出"动机 → 方法 → 关键实验 → 结论"不够。完整结构 **5 个动作**，≤400 字：

```
第 0 步 · 坐标   开山 / 演进 / 跨界替代 / 缝合
第 1 句 · 痛点   以前在 __ 场景，卡在 __ 瓶颈
第 2 句 · 手术   把原来的 A 换成了 B
第 3 句 · 疗效   最有冲击力的那一个数字：__
第 4 句 · 代价   引入了 __ 开销，落地要优化 __
```

★ **五条质量控制**（v1.3 新增，缺一会导致幻觉）：

| # | 约束 |
|---|---|
| 1 | **「坐标」是强判断，LLM 极易脑补** → 必须引用**论文内可核查事实**；无据则输出 `待定`（与定级硬约束 3 同源） |
| 2 | ★ **【疗效】的实验数字是事实不是表达** → **可自由引用，不受词数限制**（BLEU/FLOPs/加速比/参数量/准确率）。仍须注明出处章节便于回查 |
| 3 | 文字引用**每条 ≤ 100 词、全篇 ≤ 300 词**（对齐 STM/PSP 2016 学术引用指南）；完整署名、**不得改动引文** |
| 4 | ★ **图表一律不复制** → 自己重画并注明 `Adapted from Data in <作者等, 年份>` |
| 5 | **优先改写而非引用** —— 既避开版权，也符合"导出物是合成文档"的定位 |

> ⚠️ 注：**"120 秒朗读/录音"是项目负责人的个人实践，不进代码**（YAGNI）。
> 代码只做**字数约束（≤400 字）**。

### 5.5.1c ★ 背景透镜（v1.3 新增）

每篇深度分析强制回答五问。**五问抽象为通用模板，可按背景切换**：

| 通用问题 | 芯片/硬件背景 | 后端/分布式背景 | 生物/医学背景 | 产品/业务背景 |
|---|---|---|---|---|
| **瓶颈资源是什么？** | 算力/带宽/显存 | 延迟/吞吐/一致性 | 数据稀缺/标注成本 | 用户体验/成本 |
| **它把什么换成了什么？** | 访存换计算 | 一致性换延迟 | 标注换自监督 | 质量换响应速度 |
| **代价落在哪个环节？** | 额外 kernel/通信 | 运维复杂度 | 可解释性下降 | 边界 case 变差 |
| **什么条件下会失效？** | 序列短/batch 小 | 数据量小时 | 分布偏移时 | 长尾场景 |
| **这套思路能反向迁移吗？** | 稀疏化/流水线 | 调度策略 | 实验设计 | 增长策略 |

★ **三条硬约束**：
1. ★ **透镜需要正文**（FLOPs/访存/AllReduce/平台映射几乎不进摘要）→
   **只对已抓正文的论文输出**；无正文整块标 `【需正文】`，**禁止 LLM 猜**（与 §1.3 自洽）
2. **非硬件类论文允许 N/A**：benchmark/eval/RLHF 类硬套"算术强度"是强套 →
   每问允许 `N/A — 原因`，prompt 明令"宁可 N/A 不可编造"
3. **代价字段合并**：三句半给**一句话代价**，透镜给**结构化代价**（环节 + 可否优化），避免两处打架

★ **透镜做成配置**：`config/lens.yaml`，默认 `chip`，附 `generic` / `backend` 两例。
**对开源是卖点**（别人换自己的透镜）。

★ **第 5 问「能反向迁移吗」= 定级的「复用价值」判据**
→ 透镜输出可**直接作为定级输入**（免费午餐：用深度分析反推定级）。

### 5.5.2 ★ 文献定级（Tier）

> **判据与硬约束见 `src/ai_scholar/prompts/grading.j2`。**
> ⚠️ v1.3 注：三条判据 + 六条硬约束的**原文待项目负责人补入该 prompt 文件**，
> 此处只记衔接设计。

**三条判据**：复用价值 / 考察概率 / 结构权重。
**高 ≥ 2 → Tier 1；高 = 1 → Tier 2；全不高 → Tier 3。**

#### ★ Tier 的作用：是排序权重，不是门槛

> ⚠️ **原稿写「只有 Tier 1 才深度分析」，这是错的。**
> 延迟定级后新论文几个月都没有 Tier →
> 那它**永远等不到深度分析**，而"读懂今天的论文"正是核心需求。

**双通道触发**：

| 通道 | 触发 | 时效 | 预算 |
|---|---|---|---|
| **A 意图驱动**（主） | watchlist 命中 / 用户显式指定 / 当日 Top N | **立刻** | **注意力预算**（每周 5 篇）|
| B 价值驱动 | 定级后 Tier 1 | 延迟（等引用） | 进「补读经典」队列 |

**★ Tier 是新论文深度分析的排序权重，不是门槛。**

#### ★ 延迟定级（为什么不在入库时定级）

**结构权重判据需要施引数据，新论文没有** —— 立刻定级时三条判据只有两条有效。
等引用数据补齐后定级，**成本降、质量升**。
⇒ **大部分论文永远攒不到有意义的引用 → 根本不需要定级。**

**触发定级的条件（满足其一）**：
- `citation_count ≥ min_citations`（默认 5）
- 或 `published_at ≥ 180 天`（快路径：HF 翻出的旧论文直接定级）
- 或已被顶会接收（OpenReview 信号，L1+）

**★ 定级本身也有成本 → 三级预筛**

```
预筛（零成本）→  LLM 定级（fast）→  深度分析（strong）
 watchlist 命中 / venue 白名单 / 引用数信号
 明显不够格 → 直接 Tier 3
```

**★ 预筛必须兜底放行**（`prescreen_pass_ratio: 0.2`）——
不能让数据缺失导致好论文被永久判 Tier 3。

★ **正文抓取跟随深度分析触发，不按 Tier 限制**（`tiers: null` + `triggers: same_as_deep`）。

#### 5.5.2b ★ 质量评分：拆来源，不给综合分

| 组 | 字段 | 来源 |
|---|---|---|
| **客观信号** | venue、引用数、作者机构、代码可用性、有无实验 | 数据 |
| **LLM 判断** | 方法论严谨性、创新度、写作清晰度 | 模型 |

**★ 不输出单一综合分**——综合分把两种来源混成一个无法追溯的数字。
分别呈现，让用户自己权衡。

> ⚠️ **注意与 §4.2 的 `score` 区分**：`score` 是**排序用的客观信号分**
> （热度/跨源/主题相关，用于"今天先看哪篇"），
> 与这里的**质量评分**不是同一件事。**两者分列，不合并。**

### 5.5.3 成本与范围约束（硬）

| 约束 | 要求 |
|---|---|
| 范围 | **注意力预算**（每周 5 篇，可配）；**不做全量** |
| 持久化 | 结果按 content_hash 缓存，**绝不重复分析** |
| 档位 | **strong**（长链推理），max_tokens 按 **2-3 倍**设 |
| 输出紧凑 | 只返回必要字段，**不回显摘要** |
| 失败 | 分析失败 → 该段落标"—"，**不影响其他段落与整体导出** |
| ★ 超预算 | 超出 `weekly_budget` **进队列不丢弃** |

### 5.5.4 与标记块的关系（★ 易错）

| 区域 | 内容 | 重新导出时 |
|---|---|---|
| **生成区内** | 深度分析（可由系统重算） | 覆盖 |
| **生成区外** | 用户笔记（"我的笔记"） | **保留** |

**深度分析放在生成区内**——因为它是可重算的系统产物。

### 5.5.5 里程碑影响

- **L3a**：条目级 why/stance（fast 档，覆盖广）
- **L3b-1**：文献定级（fast）
- **L3b-2**：深度分析（strong，**由意图触发，不看 Tier**）

## 5.6 ★ vault 笔记边界（v1.3 新增，关键决策）

> **★ v1.7 补：选集策略定案** —— §5.6 定了"哪三类该有笔记"，但**没有机制选出它们**。
> 漏洞：默认 `export --limit 20` 取"最新 20 篇"，而每天新增 515 篇
> ⇒ **每天造 20 篇笔记 = 7,300 篇/年**，是 §5.6 目标（300–500）的 **15 倍**。
> （L1-A 实跑时已产生 40 篇笔记，是此漏洞的早期信号。）
>
> ⇒ 新增 **`papers.selected BOOLEAN`**（默认 0）：
> ① `export` **默认只导出 selected**（`--all` 才导出全量/demo 用）
> ② 置位途径：深度分析完成（L3）· 显式收藏（`ai-scholar mark`）· 从报告点读（L2）
> ③ **L1-B 先落地字段与默认行为**，置位途径随对应阶段接入
> ⚠️ 必须在 **L2 自动化之前**完成，否则每天自动跑 = 每天污染 vault。

**两个数的分工（易混，务必分清）**：

```
515/天  = 进【系统】的论文数（db 全量存，可丢弃缓存）
  5/周  = 【深度分析】篇数（注意力预算，漏斗最底出口）
```

**★ vault 独立笔记只给三类**：
1. 已深度分析的（≈260/年）
2. 显式收藏 / 点名要读的
3. 从每日报告点进去读过摘要的

**★ watchlist 命中的 230/天【不建独立笔记】** → 进每日报告 ★ 列表，
想读才生成笔记。⇒ **年增笔记约 300–500 篇**（而非 8.4 万 / 18.8 万）。

**★ 连带处理**：未建笔记的论文**不在 Obsidian 关联图里**（wiki-link 指向空）。
- 解法：深度分析笔记里由 LLM 列出它引用的**关键工作（文本 + 外链，不是 vault 笔记）**
  —— 既保住"顺着引用边探索"的可探索性，又不撑爆 vault
- 影响有限：可回 db 搜索
- **Obsidian 图的定位 = "我的阅读地图"，不是"整个文献宇宙"**（后者归 db）

### 6.1 目录结构

```
vault/
├── 00-首页.md                    # MOC 总入口
├── 10-文献/
│   └── 2026/
│       └── 2026-10-17__FDE-Gym-The-Last-Mile-of-AI-Delivery.md

│   └── 智能体评测.md              # 主题 MOC

└── 90-元数据/
    ├── links.json                # 关联数据
    └── 生成报告.md                # 每次导出的状态报告
```

**设计理由**：数字前缀保证 Obsidian 侧栏排序稳定；按年分目录避免单目录文件过多。

#### 6.1.1 ★ vault 落点（v1.4 定案）

```
~/projects/ai-scholar/          ← 代码仓库【public】
~/projects/ai-scholar-vault/    ← 知识库【private 独立仓库】
```

| 项 | 规则 |
|---|---|
| 默认输出 | `export.out_dir` = `~/projects/ai-scholar-vault` |
| ★ config 路径 | **只准 `~/` 开头**，禁止写死 `/home/<用户名>/`（① 泄露用户名 ② 别人 clone 后路径不存在） |
| 代码仓库 | `.gitignore` 加 `vault/`（**双保险**，防手滑 `git add -A`） |
| vault 备份 | ★ `git init` + private remote；`doctor` 检查无 remote 时 **warning** |

★ **为什么强调备份**：`first_seen`/`signals` 有 JSONL 落 public、db 可重采，
但**用户笔记只有 vault 一份** —— 它是全项目**唯一不可再生、不可重采、无备份**的数据。

★ **双仓库五条防护**（详见执行手册 §0.3）
① 路径不含 `/home/`、`/Users/` ② **CI 日志不打印真实路径**（日志默认公开）
③ 默认路径 ≠ `example_vault/`，写入前校验目标不在代码仓库内
④ vault 有 remote，无则 warning ⑤ vault 用 git 就不叠加 Obsidian Sync / iCloud

★ **隐性退化与对策**：真 vault 不在版本控制里 ⇒ `git diff` 检查不到它 ⇒
幂等失去自动验证（现有幂等单测跑在 tmp 目录，是**替身**不是真身）。
⇒ **`export --check`**：输出"将要变更的文件列表"，正常应为空，退出码 0/1。

**★ 生成报告不进 vault 的 git（v1.5 定案）**：加入 vault 的 `.gitignore`。

| 理由 | 说明 |
|---|---|
| **让 `git status` 成为干净信号** | 报告每次导出必变 ⇒ 若纳入跟踪，vault 仓库**永远脏** ⇒ 你会习惯性忽略 ⇒ **真正该备份的笔记变化反而看不出来**。排除报告后：`git status` 脏 = 笔记变了 = 该 commit |
| **运行历史不丢** | db 的 `runs` 表有完整的每次运行记录，生成报告只是它的**文本镜像**，不进 git 不丢任何数据 |
| 服务于头号风险 | 本项目的头号风险是"笔记是唯一副本"，备份靠 commit —— 该决定直接服务于它 |

⚠️ **已知局限**：`--check` 只校验本次选集（默认 20 篇），范围外的旧笔记不在检查内；
全量校验需 `--check --all`（**L1-B 补**）。

### 6.2 ★ 文件名清洗（必做，易踩坑）

**Obsidian / 文件系统非法字符**：`/ \ : * ? " < > |`

**规则**：
1. 非法字符替换为 `-`
2. 连续 `-` 合并为一个
3. 长度截断（默认 80 字符，**可配**）
4. **文件名带日期前缀**（`2026-10-17__`）
5. **重名兜底**：追加短 hash（取 id 前 8 位）

**★ 反例警示**：不做清洗会导致**写入失败或文件散落在错误路径**。

### 6.3 Frontmatter 规范

```yaml
---
id: arxiv-2610.22350
title: "FDE-Gym: The Last Mile of AI Delivery"
authors: ["Author A", "Author B"]
published: 2026-10-15
first_seen: 2026-10-17
source: [arxiv, hf_papers]
primary_source: arxiv
score: 84.1                  # 排序用客观信号分（见 §5.5.2b 注）
tier: null                   # 未定级；定级后为 1/2/3
tags: [论文/智能体, 论文/评测]
status: 待读                  # ★ 用户区字段，生成时不覆盖
arxiv_id: "2610.22350"
hf_score: 42                 # HF 社区热度信号
citations: 3                 # ★ 只在笔记重新生成时更新（见下）
refs_count: 38
content_rev_at: 2026-10-17   # ★ 内容级时间戳（why/note 变才更新）
llm_mode: fast               # off / fast / strong
schema_version: 1            # 格式变更时 +1
---
```

**★ 关键约定**：
- `status`（待读/在读/已读/弃读）**由用户维护，生成时不覆盖**
- **生成时保留用户已修改的字段**（读现有 frontmatter → 合并 → 写回）

★ **v1.3 修订（幂等）**：
- **文件内只留内容级时间戳**：`generated_at` → **`content_rev_at`**，
  仅当 why/note 内容变化才更新
- **导出时间移出文件**，只进 `90-元数据/生成报告.md`（★ **秒级** `YYYY-MM-DD HH:MM:SS`）
- hash 基于**每个条目的 why/note 内容**，不是"条目集合"
- ★ **幂等验收范围**（v1.4）：**文献笔记 + `00-首页.md` + `links.json`** → diff 必须为空；
  **`生成报告.md`** → **允许 diff**（它是运行日志）
- ★ **`citations` 是观测值，每次导出都更新会产生海量 diff** →
  **只在笔记被重新生成时（深度分析/定级触发）才更新**
- ★ **生成报告恢复秒级时间**（v1.4 修正）：L0-C 曾把它降级为日期级以保幂等，**这是错的**
  —— 报告就是导出时间的指定归属地，**报告是运行日志，本就该每次变**。
  正确做法是**收窄幂等验收范围**，不是削掉数据精度。
- ★ **`content_rev_at` 用日期即可**，不必到秒级（减少 diff 面）

## 7. ★ 推演与可证伪性

### 7.1 ★ 必须区分两类推演（本项目最重要的诚实性设计）

| 类型 | 可证伪？ | 处理 | 例子 |
|---|---|---|---|
| **可验证判断** | ✅ | **进记分板**，到期自动验证 | "30 天内该方向论文数将翻倍" |
| **长期趋势洞察** | ❌ | **标注为「观点」**，**不进记分板** | "智能体瓶颈已从模型转向脚手架" |

**为什么必须区分**：直接对应 aipulse 的核心教训——
**如果让不可证伪的洞察混入统计，整个评测体系会被美化，失去意义。**

> **红线**：LLM **不得**自己决定某条推演"无法验证"。
> 可证伪性由**代码判定**（是否有量化判据 + 到期日），不由模型输出。

### 7.2 可验证判断的判据模板

```
arxiv_paper_count(direction, threshold)   # 某方向 N 天内论文数达 X
entity_mentions(entity, threshold)        # 某方法被提及次数达 X
citation_reach(paper, threshold)          # 某论文被引达 X
```

### 7.3 影响分析（新能力，aipulse 没有）

对**存量论文**做影响追踪：
- 被引增长曲线（**signal 快照序列**，见 §3.7.2 采样状态机）
- 方法被后续论文采纳的程度（实体提及增长）
- **判断：这篇论文是"开创性"还是"跟风"**

**★ 这需要时间积累**，L4 实现，且**初期必须诚实标注"样本不足"**。

★ **注意**：被引增长曲线**依赖 §3.7 的 signals 时序快照**——
若不留时序流，这个功能做不了（这正是 C′ 保留 signals 的理由）。
